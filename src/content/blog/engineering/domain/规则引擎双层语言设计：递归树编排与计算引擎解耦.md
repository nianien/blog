一个规则引擎最该先做的架构决策，是把「编排」和「计算」拆成两层独立的语言。Mosika 的做法是：**结构层用一套规则 ID DSL 负责编排，计算层用 JavaScript 负责计算**——前者决定执行哪些规则、如何串并分循，后者决定每条原子规则具体算什么，两层彻底解耦、各自独立演进。这条分层同时决定了上下两层的形态：上层用递归树取代自由连线的 DAG，不再需要单独处理流程汇合点和循环体边界；下层把 JavaScript 引擎的耦合面收敛到单个包，切换计算引擎是一次局部改造而非跨全树重写。

本文沿着「双层语言 + 解耦」这条线，拆解每一层的语言设计、两层之间的接缝契约，以及解耦带来的具体结果。目标读者是写过或想写规则引擎、DSL、解释器的后端工程师。

## 一、为什么是两层语言，而不是一套脚本

**规则引擎最容易走错的第一步，是发明「一套自定义脚本语言」把编排和计算都塞进去。** 这一路径初看更省，用户只学一种语法、引擎只维护一个解析器，但它会在三处同时失效。

先看两层各自负责什么：

| 层 | 语言 | 负责 | 不负责 |
| --- | --- | --- | --- |
| 结构层 | 规则 ID DSL | 与、或、非、命中数、条件、串行、并行、循环及其作用域 | 读业务对象、算数值、调函数 |
| 计算层 | JavaScript 表达式 | 读取业务对象、调用 Java/UDF、计算并返回业务值 | 流程编排、规则组合 |

结构层决定「执行哪些规则以及如何组合」，计算层决定「每条原子规则具体做什么」。这条分界线不是风格选择，而是从三个具体代价反推得出。

**如果把完整业务 JavaScript 直接嵌进流程 DSL，会同时付出三笔代价**：

- 结构解析器被迫理解 JavaScript 的字符串、正则、对象字面量和运算符。编排语法本该只有十来个组合算子，却要背上一整门通用语言的词法负担，ANTLR 文法会迅速失控。
- UI、持久化和规则复用失去稳定的引用锚点。当一条规则就是一段内联脚本时，改一个阈值就要改所有引用它的地方，没有一个稳定的 `ruleId` 可以让画布节点、数据库记录、执行详情共同指向。
- 执行详情无法按业务规则归档。出了问题想回答「哪条规则没命中」，如果规则没有身份，只能拿到一段匿名脚本的求值结果，可解释性无从谈起。

当前设计让 DSL 只解析有限、稳定的组合语法，把复杂计算交给成熟的 JavaScript 引擎。DSL 的原子项永远是一个规则 ID，用运算符递归组合：

```text
a->(b=>c)->d
```

这段 DSL 的语义是「先执行 `a`，再并行执行 `b` 和 `c` 并等待完成，最后执行 `d`」。解析器只需要认识 `->`、`=>`、括号和规则 ID，完全不关心 `a` 背后那段 JavaScript 是在算年龄门槛还是在调用加密 UDF。

整篇文章的骨架就是这张图：上层结构 DSL 编排串并分循，下层 JavaScript 做计算，中间靠 matched/result 契约与 `$`/`$$`/`$args` 环境衔接。

![Mosika 双层语言总览：上层结构 DSL 编排串行并行分支循环，下层 JavaScript 计算与 UDF，中间由 matched/result 契约和 $/$$/$args 执行环境衔接](/images/blog/dual-language-rule-engine/two-layer.svg)

### 解耦即两条独立生命周期

两层语言在物理上分开，直接对应两条独立演进的生命周期：

```text
规则生产：领域知识 ──> RuleDefinition(ruleId, expression, desc)
                              │  稳定 ruleId 引用
                              ▼
产品编排：业务策略 ──> 命名规则流(串行 / 并行 / 分支 / 循环)
```

规则生产侧把领域知识封装成有稳定业务语义、可独立测试与复用的最小单元；产品与业务侧只基于稳定 `ruleId` 组织规则流，不感知底层表达式或实现。**技术团队沉淀规则、产品自由组合，改规则不动编排、改编排不碰规则**，同一业务语义还能被多个产品复用。

下面是 Mosika 参考控制面的原子规则库，它就是「规则生产」这条生命周期的落地形态：每条规则有稳定 `ruleId`、独立的判断条件 / 执行动作类型、以及被多少个业务场景引用的计数。`判断是否是成年人` 的表达式 `$.age >= $args.min` 直接用到了模板参数 `$args`——同一条规则可被多个场景以不同参数复用。

## 二、上层的语言设计：递归树取代 DAG

**可视化规则编排一旦允许自由连线，就会滑向 DAG，并被迫为汇合点和循环体边界付出永久的设计税。** Mosika 上层的核心选择，是用一棵递归树表达编排结构，主动放弃自由连线。

### DAG 的两个历史包袱

传统流程编排让用户在画布上拖节点、拉连线，节点之间多入多出，结构本质上是一张有向无环图。DAG 直观，但始终伴随两个问题：

**其一，需要显式设计流程汇合点。** 一个分支裂成三条并行路径后，这三条路迟早要合回一条主干继续往下走。在 DAG 里，「合回来」是一个需要用户手工连线、引擎专门识别的汇合节点（join / merge）。分支越多、嵌套越深，汇合点的维护越容易出错：漏连一条边，语义便随之改变。

**其二，需要定义循环体边界。** 循环意味着一条从后往前的回边。「循环从哪个节点开始、到哪个节点结束、哪些节点算循环体内」在 DAG 里没有天然答案，必须额外定义一套循环体边界语义。循环嵌套循环时，边界判定进一步复杂化。

这两个包袱的根源是同一个：**DAG 里结构语义部分依赖连线拓扑和画布布局，而拓扑本身没有天然的作用域边界。**

### 一棵递归树，两个递归域

Mosika 上层把编排定义成一棵递归树，只有两个递归域，通过单向连接组合：

```text
Flow = ActionNode(rule, next?)
     | ConditionNode(rule, next?)
     | SerialNode(Flow+)
     | ParallelNode(Flow+)
     | DecisionNode(ConditionNode+, default?)
     | LoopNode(max, rule, next)

Rule = AtomicNode(expr, args?)
     | BooleanNode(expr, args?, negative)
     | LogicNode(&& | ||, Rule+)
     | MatchNode(minHits, maxHits, Rule+)
```

**Flow** 是宿主递归域，承载动作、条件、串行、并行、分支、循环；**Rule** 是内嵌规则域，承载原子引用、可取反引用、与或组合、限定匹配。两个域只通过 `FlowNode.rule -> RuleNode` 单向连接：规则子树不能引用 Flow 节点，因此规则表达式不会反向携带编排关系。这条单向边是上层保持结构清晰的关键约束。

Rule 域本身也是一棵可递归组合的树。下面是「发布前质量门禁」里一个人工复核条件的规则编辑器：根节点是「条件或」，含「需要人工复核」和一个嵌套的「条件或」，后者的两个叶子「证据覆盖不足」「原创性不足」都对原子规则做了取反（标记为「非」）。每个叶子按稳定 `ruleId` 引用一条原子规则（`r10010`、`r10019` 等）。与、或、限定匹配可以互相转换、任意嵌套，叶子可整体取反，和 Flow 域的结构节点是同一套递归思路。

![Mosika 规则编辑弹窗：条件或组合的递归树，含嵌套的或与取反（非），叶子按 ruleId 引用原子规则](/images/blog/dual-language-rule-engine/rule-popup.jpg)

### 递归如何消解那两个包袱

换成递归树后，DAG 的两个历史包袱直接消失，因为**树的每个子节点天然自带作用域边界**：

**不需要设计流程汇合点。** 每个 `SerialNode`、`ParallelNode`、`DecisionNode` 都是自身子树的一等虚拟根，任意 `FlowNode` 都能作为它的一个分支。并行分支各自是一棵完整的 Flow 子树，「并发执行并在本层汇合」由结构本身表达——`ParallelNode` 的子树全部执行完，就是这一层并行的自然汇合，不需要在画布上把多条分支手工连回同一个汇合节点。

**不需要定义循环体边界。** 循环体就是 `LoopNode.next` 指向的一棵普通 Flow 子树，单根、可嵌套任意结构，天然自带边界。循环不是一种特殊连线，而是和串并分一样的递归节点，因此 `loop` 可以自然嵌套 `loop`，无需为「循环从哪开始、到哪结束」单独设计语义。

![DAG 与递归树对比：DAG 需要显式汇合点和循环体边界，递归树用子树作用域天然消解两者](/images/blog/dual-language-rule-engine/dag-vs-tree.svg)

### 代价：舍弃「直观」，换来概念统一

递归树不是没有代价。它舍弃的正是 DAG 最吸引人的那一点——**所见即所连的直观性**。用户不能再随手把任意两个节点拉一条线，结构必须显式声明为嵌套关系。`SerialNode(ParallelNode(a,b), ParallelNode(c,d))` 表示「先跑完第一组并行，再跑第二组」，这个顺序是由树的嵌套写死的，不是画布上从左到右的布局暗示的。

这笔交易值得，逐维度对比就清楚了：

| 维度 | 自由连线 DAG | 递归树 |
| --- | --- | --- |
| 汇合点 | 手工连线 + 引擎识别 | 子树完成即汇合，无需设计 |
| 循环体边界 | 额外定义边界语义 | `next` 子树单根自带边界 |
| 嵌套 | 深层嵌套易破坏拓扑 | 同类子树可无限互换嵌套 |
| 结构来源 | 部分依赖坐标与连线方向 | 显式声明，布局只服务阅读 |
| 编辑视图与执行视图 | 两套表示 | 同一棵树 |

**结构显式声明，不从画布布局、坐标或连线方向推断**，这是「图即源代码」的真正含义：UI AST 的 JSON 就是这棵树，它同时是编辑模型、持久化格式和编译输入，布局方向只服务阅读。当同类子树可以互相替换（任意 `FlowNode` 作分支、任意 `RuleNode` 作子规则），整套编排的概念自始至终只有一份，扩展新结构不会引入新的边界特例。

### 一套递归文法覆盖全部组合

上层 DSL 的运算符是一套可递归嵌套的组合算子，落到内核就是对应的节点类型：

| 语法 | 节点 | 含义 |
| --- | --- | --- |
| `!a` | `NotNode` | 对规则命中状态取反 |
| `a&&b` | `AndNode` | 逻辑与，遇未命中即短路 |
| `a\|\|b` | `OrNode` | 逻辑或，遇命中即短路 |
| `all(a,b,c)` | `AllNode` | 全部子规则命中，继承 `AndNode` |
| `any(a,b,c)` | `AnyNode` | 任一子规则命中，继承 `OrNode` |
| `some(2,_,a,b,c)` | `SomeNode` | 命中数落在 `[2, _]` 区间 |
| `a?b:c` / `a?b` | `CaseNode` | 条件选择分支（完整 / 半条件） |
| `a->b` | `SerNode` | 串行执行结构 |
| `a=>b` | `ParNode` | 并行执行结构 |
| `loop(3,cond,act)` | `LoopNode` | 条件命中则执行动作，最多三轮 |
| `_` | 命中边界 | 该侧不限制 |
| `∅` | 结构占位 | 稳定串并结构，不参与业务计算 |

`&&` 和 `||` 保留从左到右的求值顺序与短路语义；`all`、`any` 复用与/或的顺序短路实现，但保留各自的 AST 身份和稳定表达式，这种复用是单向的，`a&&b&&c` 不会被反向规范化成 `all(...)`。`loop(max, condition, action)` 是唯一的有界重复形式，不提供无界执行。全部算子可递归嵌套，一套文法即覆盖串、并、分、循的任意组合。

每个算子对应一种确定的执行结构：串行按声明顺序逐个执行，并行分裂后在本层汇合，条件按判断结果选择分支，有界循环在条件命中时重复执行动作。六种基本结构如下：

![Mosika 六种基本编排结构：串行、并行、完整条件、半条件、有序多分支、有界循环](/images/blog/dual-language-rule-engine/syntax-overview.svg)

真实业务场景就是这些结构的多层嵌套。「标准深度文章生成」把分、串、并叠了多层：顶层按内容类型分流，进入深度文章准入后是一段串行，串行内部再嵌决策与并行子树。整棵图没有一个手工连接的汇合节点，每个结构节点的子树执行完毕即为该层的自然收束。

![Mosika 标准深度文章生成场景画布：分、串、并结构节点多层递归嵌套，无手工汇合点](/images/blog/dual-language-rule-engine/canvas-nested.jpg)

### 循环与嵌套循环

许多规则引擎不支持循环。障碍通常不在执行，而在表达：在自由连线的 DAG 里，循环是一条从后往前的回边，「循环从哪个节点开始、到哪里结束、哪些节点属于循环体」没有天然答案，必须为它单独设计一套边界语义；循环嵌套循环时边界判定进一步复杂化。

在递归树里这个问题不存在。循环是一个和串、并、分同级的普通节点 `LoopNode(max, condition, next)`，循环体就是 `next` 指向的一棵完整 Flow 子树——单根、自带边界。因为循环体本身又是一棵普通子树，在它里面再放一个 `LoopNode` 就是嵌套循环，不需要任何额外机制。表达循环和表达串行一样，只是换一种节点类型。

下面是一个真实的循环场景「素材补全重试」。选中「循」节点，右侧属性面板显示它的最大循环次数（5）和循环条件（仍需补全素材）——循环不是无条件重复，而是每轮先判断循环条件，命中则执行补全动作并进入下一轮，未命中或达到轮次上限即退出；循环结束后接一个「记录生成审计」动作。循环条件、循环体、循环后续都是画布上的普通节点。

![Mosika 素材补全重试场景：选中循环节点，右侧属性面板显示最大循环次数 5 与循环条件仍需补全素材，循环体是普通子树](/images/blog/dual-language-rule-engine/canvas-loop.jpg)

递归树替换 DAG，代价是舍弃自由连线的直观，换来的是一套自始至终一致、可无限嵌套、编辑即执行的编排语言。

## 三、上层如何单向落到内核

编辑模型和执行模型是同一套语义的不同表达，不能让执行树反过来重建编辑模型。Mosika 上层到内核走的是一条严格单向的编译链路。

### 从 UI 树到 DSL 的单向编译

链路只有一个方向：

```text
UI TreeNode JSON
      │ deserialize / validateSize
      ▼
   TreeNode
      │ validate / UINodeAdapter.toRule()
      ▼
   RuleNode
      │ expr / RuleDefinition(ruleType=2)
      ▼
   RuleSuite
```

`UINodeAdapter.toRule()` 把 UI 结构映射成内核结构，映射是确定的：

| UI 结构 | 内核结构 |
| --- | --- |
| 单个 `ActionNode` | 解析 `rule.ruleExpr()` |
| 连续 `ActionNode.next` | 一个 `SerNode` |
| 无后继的 `ConditionNode` | 条件规则自身 |
| 有后继的 `ConditionNode` | `CaseNode(condition, matched)` |
| `DecisionNode` | 按条件顺序反向嵌套 `CaseNode` |
| `SerialNode` | 带 `∅` 结构占位的 `SerNode` |
| `ParallelNode` | 带 `∅` 结构占位的 `ParNode` |
| `LoopNode` | 内核 `LoopNode(max, condition, action)` |

编译只读取执行语义：节点的 `name`、选择状态、折叠状态和坐标都不进入执行树；`AtomicNode.expr` 保存的是稳定规则 ID，不复制后台那段 JavaScript 表达式。

![UI 树经 UINodeAdapter 单向编译为 RuleNode 再生成 DSL 与 RuleSuite 的链路](/images/blog/dual-language-rule-engine/compile-pipeline.svg)

### 为什么坚决不做逆向恢复

`UINodeAdapter` 只提供 `toRule()`，没有 `fromRule()`。这是刻意的：**UI AST 及其 JSON 是编辑和持久化的唯一事实来源，执行树只保留运行语义。** 一旦允许从 `RuleNode` 反推 UI 布局，就会出现两份都声称是「真相」的模型，它们迟早会不一致：某次执行优化改动了执行树结构，反推回来的 UI 便与用户原本绘制的不再吻合。

单向编译丢弃 `name`、坐标、折叠状态这些纯编辑元数据，执行需要的一切都能从 UI 树确定性地推导出来。因为只有一份真相，画布上高亮的执行路径才可信——它执行的就是编辑的那棵树。

下面这张「内容生成任务智能路由」画布，正是编辑视图与执行结构合一的直观例子：一个「分」决策节点带四条条件分支（六边形），命中的分支各自接一个动作节点。用户在画布上看到的这棵树，就是内核实际执行的那棵树，没有第二份表示。

### 在线试运行与执行路径可视化

编辑视图就是执行树，带来一个直接可用的能力：编辑器可以对当前 UI 树发起试运行——编译成 `RuleNode` 后在内核执行，回传递归的 `RuleResult` 树，画布随即高亮实际走过的路径。命中与未命中的分支、并行的各条分支、循环的每一轮，都在同一棵树上呈现。

高亮的就是编辑的那棵树，因此这条路径可直接用于排查：为什么走了这个分支、循环跑了几轮、每个节点的返回值和动态描述是什么，都落在同一棵树上。可编排、可执行、可解释在这里收敛为一件事。

### ∅：稳定结构的占位符

`SerialNode` 和 `ParallelNode` 编译时会带上 `∅` 结构占位。`∅` 是结构标记，用于稳定串并结构、不参与业务计算。当一个流程需要以并行结构开头、之后再进入串行步骤时，用 `∅` 稳定外层串行根：

```text
∅->(a=>b)->c
```

解析结果是：

```text
SerNode(
  ∅,
  ParNode(a, b),
  c
)
```

`∅` 让「以某种结构开头」这类边界情况不必引入特殊语法，结构层的组合规律保持完整。这是递归树设计一致性的一个小而典型的体现：连占位都是一个普通的、可被递归组合的规则。

## 四、两层的接缝：契约与执行环境

**两层语言解耦得再干净，也需要一道定义清晰的接缝，让上层的控制流和下层的计算结果准确对接。** 这道接缝由三部分构成：`matched`/`result` 结果契约、`$`/`$$`/`$args` 执行环境、模板参数化。

### matched 与 result 必须分离

任意节点都可能同时具备两个维度：它作为条件时是否命中；它实际产生了什么业务值。因此 `EvalResult` 同时保存两个字段：

| 字段 | 含义 |
| --- | --- |
| `matched` | 逻辑或控制状态 |
| `result` | 业务返回值 |

**二者不能互相替代，责任必须分开。** 逻辑节点主要解释 `matched`；条件分支和动作可能传递 `result`；串并行结构只表示执行完成。各类节点的职责分工是明确的：

- 逻辑节点 `AndNode`、`OrNode`、`AllNode`、`AnyNode`、`NotNode`、`SomeNode` 解释子节点的 `matched` 并短路，返回值只表达逻辑判断，不透传某个子节点的业务 `result`。
- 条件节点 `CaseNode` 先访问条件，只执行被选中的分支，并传递该分支的 `result` 和 `matched`。
- 执行结构 `SerNode`、`ParNode` 正常完成统一返回 `result=null, matched=true`，从不因某个子节点未命中而中断或聚合。

这条分离带来一个硬约束：**规则未命中是正常业务状态，执行异常是失败，二者必须继续分离，异常正常向上传播。** 结构节点绝不把异常转换成「未命中」——如果吞掉异常返回未命中，一次数据库超时就会被误读成「规则不匹配」，排查时永远找不到真正的故障点。

这也是为什么诊断信息不能塞进 `result`：`result` 是业务返回值，往里塞状态会污染业务语义。需要传递解释性信息时，走 `$$` 上下文，由规则描述这段可执行表达式渲染。

### 三个稳定绑定：$ / $$ / $args

上层的参数如何进到下层的 JavaScript？靠三个语义明确、生命周期分明的运行时绑定：

| 名称 | 生命周期 | 含义 |
| --- | --- | --- |
| `$` | 本次顶层执行 | 业务输入对象，即 `RuleVisitor.data` |
| `$$` | 本次顶层执行 | 共享的可变规则上下文，即 `RuleVisitor` |
| `$args` | 当前原子规则节点 | 当前节点绑定的模板参数对象 |

一条原子规则的 JavaScript 就在这三个绑定之上计算：

```javascript
$.input > $args.limit
```

这三者是接缝的数据通道：`$` 送入上层的业务输入，`$args` 送入节点绑定的模板参数，`$$` 承载规则之间的共享读写。它们符号特征明显，不容易和普通业务字段冲突，也让规则文本保持紧凑。

`$` 和 `$$` 活在整次顶层执行，`$args` 只活在当前原子规则节点。这个生命周期差异是模板参数化的基础。

### 模板参数化：一条规则，多组参数

只有阈值、等级、地域不同的判断，过去要复制成多条几乎相同的规则定义：

```text
多条重复定义：            一条模板定义：
r1 = $.input > 100        threshold = $.input > $args.limit
r2 = $.input > 200
r3 = $.input > 300
```

现在只定义一条模板，在规则 ID DSL 的原子节点上按节点绑定不同参数：

```text
threshold("""{"limit":100}""") || threshold("""{"limit":300}""")
```

三引号包围一段 JSON 对象文本。ANTLR4 只识别三引号参数块的安全边界，不解析 JSON 内部结构——参数不是 JavaScript 源码片段，不会被拼接或替换进规则表达式，从根上杜绝了注入。`ExprNode` 在构造时通过一次解析把参数转成 `Map`，并用规范化 JSON 生成完整的 `expr()`，执行阶段不再重复解析。

模板参数化的缓存语义值得引擎作者留意：**缓存键是 `ruleId` 加规范化 JSON，对象字段递归排序、数组顺序保留，相同参数组合在一次顶层执行内只求值一次。**

```text
r001("""{"limit":100}""") -> r001("""{"limit":100}""")
```

上面两次调用只真正求值一次，但仍分别生成执行节点、各自保存结果和动态描述——参数化调用的执行详情不合并。规则 JavaScript 的 `Script` 按稳定的 `expression` 预编译并复用，不为每组参数重新编译；参数只在执行时绑定为 `$args`。一份编译产物，多组参数实例化，这是解耦在计算层的又一次兑现：规则定义只表达稳定逻辑，节点只提供本次调用的配置。

## 五、下层的语言设计：JavaScript 与引擎收敛

下层要把计算做扎实，同时让「用哪个计算引擎」成为一个可以随时替换的局部决策。Mosika 选 JavaScript 做计算层语言、Rhino 做当前实现，并把引擎耦合收敛到一个包里。

### 为什么计算层选 JavaScript

计算层要读业务对象、算数值、返回结构化结果，这需要一门有成熟解析器、支持对象字面量和闭包的语言。JavaScript 满足全部条件，且规则作者普遍熟悉。一条规则可以直接返回对象字面量：

```javascript
{stage: "CLAIM_EXTRACTION", status: "completed", claimCount: $.claimCount}
```

引擎会在编译边界自动为顶层对象字面量补分组括号，规则作者不必手写 `({...})` 来避免它被解析成代码块。其他表达式原样编译。

### 可信执行边界是产品能力

一个容易被误判的设计点：**规则表达式不是面向不可信用户的安全模板，而是可执行 JavaScript，Java 互操作是产品能力，不是需要消除的暴露面。** 设计上允许规则访问 Java 对象属性和方法、使用 `Java.type(...)`、传递和返回 `BigDecimal` 等 Java 类型：

```javascript
$.amount.add(new (Java.type('java.math.BigDecimal'))('1.00'))
```

`mosika-core` 全部是进程内代码，不是对外 SDK，所有调用方都在同一仓库里，参数来源可追溯。因此 Rhino 的 Java 互操作能力被当作能力用，而不是当作漏洞防。如果调用方确实需要不可信脚本隔离，应在内核外另建授权与运行边界，而不是靠缩减表达式语义实现——这条边界划在哪里，本身就是解耦思想的一部分：内核只管把计算做强，安全隔离是产品层的事。

### 求值收敛到 RuleEngine.doEval

「用什么引擎计算」在内核里收敛到一个点。无论是原子规则、临时表达式还是动态描述，全部求值都经由 `RuleEngine` 的三个公开方法 `evalRule` / `evalExpr` / `evalRuleDesc`，最终落到同一个私有方法 `doEval`：

```java
private Object doEval(Object script, Object root, Object ruleContext,
                      Map<String, Object> arguments) {
    return RhinoEngine.evaluate(script, udfScope, root, ruleContext, arguments);
}
```

`doEval` 是唯一的求值收敛点：脚本与作用域都以 `Object` 类型持有，只有 `RhinoEngine` 这一层知道它们真实的 Rhino 类型（`Script`、`Scriptable`、`Context`）。整棵求值树（`RuleNode`、`RuleVisitor`、`EvalCacheScope`）只调 `context.eval(this)`，节点类型里从不出现引擎类型，把「用什么引擎算」完全交给 `doEval` 委托出去的那一层。

这一点可以用一次 grep 验证：`mosika-core` 里引用 Rhino（`RhinoEngine` 或 `org.mozilla`）的文件只有四个，全部在 `engine/` 与 `engine/rhino/` 包内；结构层、装配层、UDF 抽象层（`eval/`、`suite/`、`udf/`）一处都不涉及。

![所有求值收敛到 RuleEngine.doEval：结构层只调 context.eval，三个求值入口汇聚到 doEval，再委托给可替换的 RhinoEngine 四个入口](/images/blog/dual-language-rule-engine/engine-coupling.svg)

### 因此切换引擎是局部改造

求值收敛到一个方法带来一个直接结果：**换引擎不是跨全树重写，而是替换 `doEval` 委托出去的那一层。** `RuleEngine` 对引擎的全部依赖只有四个入口——`compile`、`evaluate`、`inContext`、`sharedScope`。把它们从 `RhinoEngine` 的静态调用提成一个接口，再补上 GraalJS 或 QuickJS 的实现，改造范围就到此为止：

| 切换引擎时 | 是否改动 |
| --- | --- |
| `engine/rhino/` 三个类（RhinoEngine / JsUdf / JavaUdfFunction） | 重写 |
| `RuleEngine` 对 compile / evaluate / inContext / sharedScope 的调用 | 改指向新实现 |
| 全部 RuleNode、逻辑 / 流程 / 条件节点语义 | 不动 |
| RuleVisitor、缓存作用域、执行详情树 | 不动 |
| DSL 文法、UI 树、单向编译 | 不动 |
| UdfContainer 引擎中立的 POJO 树 | 不动 |

需要说明的是，Mosika 今天并没有定义正式的引擎 SPI 接口，也没有做多引擎热插拔。它做到的是「耦合收敛」而非「插件化」，两者的区别很实在：耦合收敛意味着替换成本可控、局部、可估算，而不必为一个可能永远不来的第二引擎预先付出抽象接口的复杂度。等真的需要第二个引擎时，把 `RhinoEngine` 的方法签名提成接口即可，改造范围就是上表那两行。

### 编译缓存与执行作用域

计算层的性能来自「编译一次、执行多次」。`RuleEngine` 在 `RuleSuite` 构造阶段把 `ruleType=0` 的原子规则预编译成 Rhino `Script`，缓存值是可跨 Rhino `Context` 和线程复用的编译产物：

| 缓存 | 键 | 用途 |
| --- | --- | --- |
| `compiledScripts` | JavaScript 源码 | 原子规则构造期去重及运行期缓存 |
| `compiledRules` | `ruleId` | 已注册原子规则脚本索引 |
| `compiledDesc` | 描述模板文本 | 构造期描述模板去重 |
| `compiledRuleDesc` | `ruleId` | 已注册规则描述脚本索引 |

执行阶段每次脚本求值：复用当前线程已进入的 Rhino `Context`；创建以当前 `RuleEngine` 的 UDF 共享作用域为原型的独立子作用域；在子作用域中绑定 `$`、`$$`、`$args`，UDF 通过原型链读取；直接执行预编译 `Script`。规则顶层变量和 `globalThis` 状态不会带到下一次执行，一次规则流的多段脚本复用一个 `Context`，并行分支在工作线程中分别进入自己的 `Context`。

**编译配置与单次执行状态分离**是这套缓存能安全并发的前提：套件生命周期持有编译产物与 UDF 共享作用域，顶层求值生命周期持有 `RuleVisitor` 与当前线程 Context，脚本求值生命周期持有独立子作用域和三个绑定。三层生命周期不交叉，预编译产物只读共享，可变状态各自隔离。

## 六、UDF：一等能力，也是解耦的产物

UDF 是内核的一等扩展机制，它的实现方式也是「抽象与绑定分离」这条解耦原则的又一次应用。是内核先支持了 UDF，上层编排才谈得上「在规则里调用函数」。

### UdfContainer 引擎中立

UDF 用统一的声明模型描述，不区分 Java 和 JavaScript 的外部注册方式：

```text
group  可选分组路径，例如 content.generation
name   UDF 名称，例如 eval
udf    Java 对象或 JavaScript 源码字符串
```

分组用点号形成多级命名空间，`UdfContainer` 把它拆成嵌套 Map。关键设计在于：**`UdfContainer.compile()` 的产物是纯 POJO 对象图，不引用任何 Rhino 类型。** 抽象层只描述「有哪些 UDF、怎么分组」，完全不碰「用什么引擎绑定」。

Rhino 绑定由 `RuleEngine` 在构造时通过引擎提供的编译回调完成：递归创建 Rhino `NativeObject`，Java UDF 叶子绑定为 `JavaUdfFunction`，JavaScript UDF 叶子绑定为 Rhino `Function`，全部绑定后封闭为只读共享。这里是同一条「抽象与绑定分离」的边界：**UDF 的「是什么」是引擎中立的，「怎么在某引擎里跑」才落到 `engine/rhino/`。** 换引擎时，`UdfContainer` 这棵 POJO 树一行不动。

### 两种 UDF，一套调用语法

UDF 分 Java 与 JavaScript 两类，但在规则表达式里的调用语法完全一致：`udf(...)` 直接调用，`udf.method(...)` 调具名方法，`group.sub.udf(...)` 走分组命名空间。JavaScript UDF 是一段源码字符串，和调用它的规则在同一个 Rhino `Context` 中执行；Java UDF 是一个普通 Java 对象，通过 `UdfDelegate` 受控暴露。规则作者无需知道某个函数底层是 JS 还是 Java。

### Java 方法按元数重载

`UdfDelegate` 只收集带 `@UdfMethod` 的 public 实例方法，按「方法名 + 形参个数」建立索引。**同名方法只要形参个数不同即可共存；同名且形参个数相同的两个签名在代理构造期直接被拒绝**（`ambiguous udf method`）。这不是 Java 的按参数类型重载，而是按元数（arity）重载，外加一个可选的 varargs 兜底。

调用时先按实参个数精确匹配定长签名，未命中再回退到 varargs：

```java
class ReplaceUdf {
    @UdfMethod String apply(String s, String from, String to) { ... }   // 三参精确匹配
    @UdfMethod String apply(String s, String... parts)        { ... }   // 其余回退 varargs
}
```

规则里 `replace($.text, "a", "b")` 命中三参签名，`replace($.text, "a", "b", "c")` 因没有四参定长项而回退到 varargs。分派规则简单可预测，不引入 Java 重载解析的复杂度。

### 像 JS 一样调用 Java

规则作者写的是 JavaScript，却能像调普通 JS 函数一样调用 Java UDF——**参数与返回值的类型转换由 `UdfDelegate` 按目标方法的泛型签名自动完成。** JS 传入的值按目标形参类型经 JSON 反序列化成对应的 Java 类型（`List`、`Map`、Bean、`BigDecimal` 等），Java 的返回值再转回 JS 值：

```javascript
sys.num.divide("0.1", "0.2", 2)     // 传字符串，底层用 Java BigDecimal 精确相除
sys.coll.sum($.amounts)             // 传 JS 数组，底层收成 Java List
```

规则作者看到的是简洁的函数调用，底层跑的是 Java 的精确数值与类型能力。UDF 还能作为另一个 UDF 的参数传入，按目标类型转成原始 Java 对象或统一的 `java.util.function.Function`。

内置库 `mosika-udf` 就是这样一组挂在保留分组 `sys` 下的 Java UDF，锚定 JavaScript 做不到或不可靠的能力：

| 分组 | 能力 | 示例 |
| --- | --- | --- |
| `sys.num` | `BigDecimal` 精确运算 | `sys.num.divide(a, b, 2)` |
| `sys.date` | `java.time` 日期 | `sys.date.daysBetween(a, b)` |
| `sys.crypto` | 哈希 / HMAC / Base64 | `sys.crypto.sha256(s)` |
| `sys.text` | Java 正则 / Unicode | `sys.text.normalize(s)` |
| `sys.coll` | 集合运算 | `sys.coll.sum(list)` |
| `sys.id` | 标识 / 随机 | `sys.id.uuid()` |

`double` 无法精确表示金额、`Date` 时区解析不可靠、Rhino 没有加密能力、正则与 Unicode 语义有差异，内置库用 Java 能力补齐这些短板。计算层因此可以持续扩展，而扩展方式引擎中立：新增一个 UDF 既不碰引擎，也不碰结构层。

## 七、设计权衡与适用边界

双层语言加解耦这条线，落到上层、下层和协作三处，各自有可以直接观察到的结果。

**上层：递归树带来概念统一。** 编排层不必迁就计算语言，可以选对编排最自然的模型。选了递归树之后，DAG 的汇合点和循环体边界不再需要单独设计，编排语言可无限嵌套，编辑视图与执行视图是同一棵树。代价是舍弃自由连线的直观。

**下层：计算引擎可局部替换。** 结构层不感知 JS 引擎，Rhino 耦合落在四个文件里，切换到 GraalJS 或 QuickJS 只改写一个包、结构层不动。替换成本可验证、可估算，而非一句口号式的「支持多引擎」。

**协作：两条生命周期独立演进。** 规则生产与产品编排各自演进，技术团队沉淀规则、产品组合规则；引擎升级与规则内容互不牵连，局部修改不影响整体。

这套设计也有明确的边界，一并列清楚：

| 项 | 状态 |
| --- | --- |
| 递归树 | 舍弃自由连线直观性，换概念统一 |
| 多引擎 | 耦合收敛可局部替换，非现成 SPI/热插拔 |
| 可信边界 | 规则作者可信是设计假设，不可信场景需外层隔离 |
| 执行超时 | 内核不提供脚本墙钟超时，阻塞需 UDF 自控 |
| 部署形态 | 进程内内核，跨进程/多租户能力由产品层补齐 |

规则引擎的分层不在模块图上，而在语言上。把编排和计算拆成两门解耦的语言，上层就能用递归树替代 DAG，下层就能把计算引擎当作可替换的实现——这两个结果都来自同一个分层决策。
